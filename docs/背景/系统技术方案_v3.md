# 化学部检测报告系统 — 完整技术方案 v3

> 版本：v3.0（融合老师方案 v2 + 用户深化讨论）
> 适用对象：广电计量化学部、材料部实验室
> 核心思想：**提取 + 可视化编辑 + Typst 渲染 + 字段映射**
> 状态：待 PoC 验证后启动正式开发

## 〇、版本演进与本方案定位

```
v1（早期）  docx 占位符 + 字段映射 + 公式编辑器
     ↓ 老师否决（docx 走不下去）
v2（老师）  Typst + 契约论 + 机器学习自动转换存量模板
     ↓ 用户深化（提取 + 编辑更优）
v3（本方案）提取 + 可视化编辑 + Typst 渲染 + 字段映射
```

**核心转变**：
- 把 Excel 从"渲染载体"降级为"信息源"
- 用 Typst 作为统一渲染引擎（原始记录 + 报告）
- 原始记录与报告两侧都用相同的"左编辑右渲染"交互
- 从原始记录到报告的字段映射<由文员可视化配置>

## 三、原始记录模板：从提取到使用

### 3.1 Excel/Word 字段提取

#### 3.1.1 提取目标

| 对象 | 提取什么 |
|---|---|
| 合并单元格 | "项目名"（通常跨列的是项目标题） |
| 普通单元格 | "字段标签"和"值的位置" |
| 方框 `□` | 单选/复选项 |
| 单位（℃/mm/MPa）| 字段单位 |
| 层级缩进 | 字段之间的父子关系 |
| 表格结构 | 重复字段的行列模式 |

#### 3.1.2 三层提取策略

**Layer 1：规则识别（快速路径）**

```python
import openpyxl
import re

wb = openpyxl.load_workbook("template.xlsx")
ws = wb.active

for row in ws.iter_rows():
    for cell in row:
        text = str(cell.value or "")

        # 项目名：短词 + 冒号结尾
        if text.endswith("：") or text.endswith(":"):
            add_field_label(text, cell.coordinate)

        # 选项：包含 □ 或 ○
        if "□" in text or "○" in text:
            extract_options(text)

        # 单位：以 ℃/mm/MPa/%/s/h 等结尾
        if re.search(r"(℃|mm|MPa|%RH|h|kg|g)$", text):
            mark_unit(text)
```

**Layer 2：LLM 语义增强**

把 Layer 1 提取出的原始字段列表喂给 Claude/GPT：

```
输入: [
  "预处理条件:",
  "(23±2)℃, (50±5)%RH, __h",
  "□ 预处理后 → (23±2)℃, 干燥器中至少 24h"
]

输出: {
  "group": "预处理条件",
  "fields": [
    {"label": "温度", "type": "number", "unit": "℃", "default": "23±2"},
    {"label": "湿度", "type": "number", "unit": "%RH", "default": "50±5"},
    {"label": "时长", "type": "number", "unit": "h"},
    {"label": "预处理后条件", "type": "checkbox", "options": ["预处理后→(23±2)℃, 干燥器中至少24h"]}
  ]
}
```

**Layer 3：人工校正（兜底）**

前端展示提取结果，工程师**点点拖拖**就能改，不用写代码。

#### 3.1.3 精度目标

用户已确认：**80~90% 自动正确**，剩余 10~20% 由工程师在可视化编辑器手改。

#### 3.3.5 计算字段与公式编辑（原始记录侧）

##### 3.3.5.1 原始记录里的典型公式场景

| 场景 | 示例字段 | 公式 |
|---|---|---|
| 多试样平均 | 平均值 | `average(test_t1, test_t2, test_t3)` |
| 多试样总和 | 总量 | `sum(pah1..pah14)` |
| 阈值判定 | 结论 | `avg_temp >= 85 ? '合格' : '不合格'` |
| 范围判定 | 结论 | `value in [lower, upper] ? '合格' : '不合格'` |
| 单位换算 | ppm 值 | `value * 1000`（mg/kg → ppm）|
| N.D. 处理 | 修正值 | `value === 'N.D.' ? 0 : Number(value)` |
| 百分比 | 占比 | `actual / total * 100` |
| 取整/格式化 | 报出值 | `round(t_avg, 1)` |
| 多字段判定 | 整体结论 | 任一不合格 → 整体不合格 |

原始记录中的公式字段和报告里的公式字段**完全同构**，可共用同一套预设公式库和执行引擎。

##### 3.3.5.4 公式执行时机

```
工程师录入 test_t1 = 85
        ↓ onChange
系统扫描所有计算字段的公式依赖
        ↓
找出依赖 test_t1 的字段：avg_temp
        ↓
再找出依赖 avg_temp 的字段：conclusion
        ↓
按拓扑排序顺序执行:
  avg_temp = (85 + test_t2 + test_t3) / 3  （若 t2/t3 已填）
  conclusion = avg_temp >= 85 ? '合格' : '不合格'
        ↓
更新前端显示（右侧 Typst PDF 也同步刷新）
```

**拓扑排序**保证依赖顺序正确。循环依赖（A 依赖 B，B 依赖 A）在模板保存时检测并报错。

##### 3.3.5.5 数据存储

计算结果与原始录入数据分开存，**双写**便于审计：

```json
{
  "raw_data": {           // 工程师实际录入的字段
    "test_t1": 85,
    "test_t2": 86,
    "test_t3": 84
  },
  "derived_data": {       // 系统计算出的字段（缓存）
    "avg_temp": 85.00,
    "conclusion": "合格"
  }
}
```

**为什么双写**：
- 未来公式修改后，可以基于 raw_data 重新计算，不丢历史
- 审计/复核时能看到录入值 vs 计算值分离
- 报告生成时两者都可被映射引用

##### 3.3.5.6 公式引擎共享

原始记录侧的公式编辑和报告侧的公式编辑，**共用同一个前端组件 `FormulaEditor` 和后端执行器**：

```
client/src/components/FieldMappingEditor/FormulaEditor.tsx
                          ↑
                          │ 同一个组件
                          │
    ┌─────────────────────┴─────────────────────┐
    │                                           │
原始记录编辑器（添加计算字段）           报告映射编辑器（配置占位符公式）
```

后端：
```
server/src/services/formula-engine.ts
  - FORMULA_TYPES: 12 个预设公式
  - execute(formula, data): 执行引擎
  - topologicalOrder(fields): 拓扑排序
  - detectCycles(fields): 循环依赖检测
```

##### 3.3.5.7 Typst 代码生成

计算字段在 Typst 里也声明成变量，由系统在数据注入时计算好再塞进 preamble：

```typst
#let data = (
  test_t1: 85,
  test_t2: 86,
  test_t3: 84,
  avg_temp: 85.00,       // 系统计算，工程师不录
  conclusion: "合格",    // 系统计算
)
```

这样 Typst 侧**完全不需要知道公式的存在**，只用变量。公式逻辑全在我们的引擎里，保证计算一致性。

##### 3.3.5.8 与报告侧的统一

| 维度 | 原始记录侧 | 报告侧 |
|---|---|---|
| 触发时机 | 模板设计时添加字段 | 模板映射时配置占位符 |
| 数据源 | 同一模板内其他字段 | 跨委托单/样品/实验数据 |
| 预设公式 | 同 12 个 | 同 12 个 |
| 编辑组件 | FormulaEditor | FormulaEditor（同一组件）|

### 6.3 组件实现要点

#### 6.3.1 React 组件结构

```typescript
// TypstViewer.tsx
import { useEffect, useState, useRef } from 'react';
import Editor from '@monaco-editor/react';
import { compile } from './typst-compiler';
import debounce from 'lodash/debounce';

interface TypstViewerProps {
  source: string;
  data?: Record<string, any>;
  mode?: 'view' | 'edit' | 'split';
  onChange?: (source: string) => void;
  height?: string;
  showSource?: boolean;
  companyTheme?: 'record' | 'report';   // 排版规范
}

export default function TypstViewer({
  source,
  data,
  mode = 'split',
  onChange,
  height = '600px',
  companyTheme = 'record',
}: TypstViewerProps) {
  const [pdfUrl, setPdfUrl] = useState<string>('');
  const [error, setError] = useState<string | null>(null);

  const compileDebounced = useRef(
    debounce(async (src: string, payload?: any) => {
      try {
        const finalSrc = injectData(src, payload, companyTheme);
        const blob = await compile(finalSrc);
        setPdfUrl(URL.createObjectURL(blob));
        setError(null);
      } catch (e: any) {
        setError(e.message);
      }
    }, 500)
  ).current;

  useEffect(() => {
    compileDebounced(source, data);
  }, [source, data, companyTheme]);

  if (mode === 'view') {
    return <iframe src={pdfUrl} style={{ width: '100%', height }} />;
  }

  if (mode === 'edit') {
    return (
      <Editor
        height={height}
        language="typst"
        value={source}
        onChange={(v) => onChange?.(v || '')}
      />
    );
  }

  // split mode
  return (
    <div style={{ display: 'flex', height }}>
      <div style={{ flex: 1 }}>
        <Editor
          height="100%"
          language="typst"
          value={source}
          onChange={(v) => onChange?.(v || '')}
        />
      </div>
      <div style={{ flex: 1, borderLeft: '1px solid #ddd' }}>
        {error
          ? <div style={{ padding: 16, color: 'red' }}>{error}</div>
          : <iframe src={pdfUrl} style={{ width: '100%', height: '100%' }} />
        }
      </div>
    </div>
  );
}
```

#### 6.3.2 编译方案

**方案 A：服务端编译（推荐生产）**

```
前端发 Typst 源码 → 后端 Node.js → spawn typst CLI → 返回 PDF Buffer
```

优点：
- 兼容性好
- 可统一管理字体/包
- 安全（不让客户端跑任意代码）

缺点：
- 网络往返延迟（500ms 内可控）
- 服务端开销

**方案 B：浏览器内 WASM（实验性）**

用 [`@myriaddreamin/typst-ts`](https://github.com/Myriad-Dreamin/typst.ts) 在浏览器内直接编译。

优点：
- 零延迟
- 不占服务器

缺点：
- 包体积大（~10MB）
- 字体加载麻烦
- 部分语法不支持

**推荐：方案 A 起步，方案 B 备选**。

#### 6.3.3 数据注入机制

```typescript
function injectData(
  source: string,
  data: Record<string, any> | undefined,
  theme: 'record' | 'report'
): string {
  if (!data) return wrapWithTheme(source, theme);

  // 把 data 转成 Typst preamble
  const preamble = Object.entries(data)
    .map(([k, v]) => `#let ${k} = ${toTypstValue(v)}`)
    .join('\n');

  return wrapWithTheme(`${preamble}\n\n${source}`, theme);
}

function wrapWithTheme(source: string, theme: string): string {
  return `#import "@gdjl/${theme}-theme:1.0.0": *\n${source}`;
}

function toTypstValue(v: any): string {
  if (v === null || v === undefined) return 'none';
  if (typeof v === 'number') return String(v);
  if (typeof v === 'string') return `"${v.replace(/"/g, '\\"')}"`;
  if (Array.isArray(v)) return `(${v.map(toTypstValue).join(', ')})`;
  if (typeof v === 'object') {
    return `(${Object.entries(v).map(([k, val]) => `${k}: ${toTypstValue(val)}`).join(', ')})`;
  }
  return 'none';
}
```

#### 6.3.4 性能优化

- **防抖编译**：500ms 内多次修改只编译一次
- **缓存**：相同源码 + 相同数据 → 直接返回缓存 PDF
- **增量编译**：仅当 source 变化时重新编译；data 变化时只重新填值
- **Loading 状态**：编译期间 PDF 区域显示骨架屏

### 7.2 生成器实现

```typescript
function generateTypst(template: RecordTemplate): string {
  const lines: string[] = [];

  // 头部
  lines.push(`#import "@gdjl/record-theme:1.0.0": *`);
  lines.push(`#show: report-template.with(`);
  lines.push(`  title: "${template.name}",`);
  lines.push(`  org: "广电计量化学部"`);
  lines.push(`)`);
  lines.push('');

  // preamble: 声明所有字段为 none（运行时被覆盖）
  lines.push(`#let data = (`);
  for (const f of allFields(template)) {
    lines.push(`  ${f.code}: none,`);
  }
  lines.push(`)`);
  lines.push('');

  // 每个分组
  for (const group of template.groups) {
    lines.push(`#section[${group.label}][`);

    switch (group.layout) {
      case 'vertical':
        for (const f of group.fields) {
          lines.push(`  #field("${f.label}", data.${f.code}${f.unit ? `, unit: "${f.unit}"` : ''})`);
        }
        break;
      case 'inline':
        const args = group.fields.map(f =>
          `("${f.label}", data.${f.code}, "${f.unit || ''}")`
        ).join(', ');
        lines.push(`  #inline-fields(${args})`);
        break;
      case 'table':
        lines.push(`  #result-table(`);
        lines.push(`    headers: (${group.columns.map(c => `"${c}"`).join(', ')}),`);
        lines.push(`    rows: (`);
        for (const f of group.fields) {
          lines.push(`      ("${f.label}", data.${f.code}),`);
        }
        lines.push(`    ),`);
        lines.push(`  )`);
        break;
      case 'two-col':
        lines.push(`  #grid(columns: (1fr, 1fr), column-gutter: 12pt,`);
        for (const f of group.fields) {
          lines.push(`    #field("${f.label}", data.${f.code}),`);
        }
        lines.push(`  )`);
        break;
    }

    lines.push(`]`);
    lines.push('');
  }

  return lines.join('\n');
}
```

**工程师永远不需要看这些代码**，他们只在可视化界面操作。

## 八、存量模板批量处理

### 8.1 流程

```
1. 业务方打包所有现有 Excel/Word 模板（几千张）
2. 写脚本批量调用提取器（Layer 1+2）
3. 输出每个模板的 JSON 字段定义 + Typst 源码
4. 生成 PDF 与原模板 PDF 比对
5. 自动通过的入库；不通过的标记待人工
6. 工程师在编辑器里调整不通过的
7. 全部入库
```

### 8.2 自动比对（机器学习兜底）

参考老师的方案，**作为存量批量处理的兜底**：

```
原模板渲染 PNG ──┐
                 ├── pixelmatch / SSIM ──→ 误差信号
Typst 渲染 PNG ──┘
                              ↓
                      调整 Typst 源码（启发式 + LLM）
                              ↓
                      重新渲染 → 再比对
                              ↓
                      迭代直到误差 < 阈值
```

**注意**：这个迭代仅用于**视觉上对齐原模板**。我们的核心方案不依赖它，只是"如果业务方坚持要保留原模板风格"时启用。

### 8.3 时间预算

| 阶段 | 时间 |
|---|---|
| 收集存量模板 | 3-5 天 |
| 写提取脚本 | 5 天 |
| 跑批量提取 | 1-2 天 |
| 自动通过率（80~90%） | 即得 |
| 人工补正剩余 10~20% | 5-7 天（多人并行） |
| **合计** | **2-3 周内全部入库** |

  onChange={(src) => updateTemplate({ typst_source: src })}
  height="100vh"
  companyTheme="record"
/>
```

**5 种使用场景，1 个组件搞定**。这就是组件化的力量。

---

## 二十二、结语

v3 方案的核心是**三个分离 + 一个统一**：

- **数据与渲染分离**：JSONB 存数据，Typst 负责渲染
- **编辑与展示分离**：左可视化编辑，右 PDF 实时预览
- **业务与样式分离**：业务在字段定义，样式在 Typst 包

- **统一引擎**：Typst 渲染原始记录、报告、任何中间产物

做好这一点，画模板的过程消失了，工程师/文员不再是"低效操作员"，系统真正成为"信息流的水管"。

PoC 完成后立即推进全量开发，6 月初上线，**速度战胜灵活，结构战胜手工**。
